# Устройство internal/vpp

Всё в одном пакете `internal/vpp`. Ниже — что делает каждый файл (без тестов).

| Файл | Назначение |
|------|------------|
| `contracts.go` | Интерфейсы `FileSystem` (чтение + обход дерева) и `FileSink` (запись/удаление вывода). Абстрагируют доступ к диску от остальной логики. |
| `osfs.go` | `OSFileSystem` — реализация `FileSystem`/`FileSink` поверх реального `os`/`filepath`. |
| `model.go` | Базовые типы домена: `Kind` (виды директив препроцессора), `Directive`, `CommentSpan`, `FileReport`, `Location`, `MacroInfo` с методами вроде `DefinedActive`/`ReferencedActive`. |
| `lexer.go` | `ScanSource` — построчный лексер Verilog/SystemVerilog: находит директивы (`` `define``, `` `ifdef`` и т.д.), строки, комментарии (диапазоны и тех и других попадают в `FileReport`), отслеживает вложенность и границы макро-тел. |
| `scanner.go` | `Scanner` — обходит папку (`ScanDir`) или список файлов из `.files` (`ScanFiles`) параллельно пулом воркеров, фильтрует по расширениям и пропускает служебные директории. |
| `summary.go` | `BuildSummary` — агрегирует отчёты по файлам в единую сводку: счётчики по видам директив, карта макросов, списки проблем (используется, но не определено; определено только в комментарии; определено, но не используется; встречается только в условиях). |
| `emptiness.go` | `AnalyzeEmptiness` — определяет, стал ли файл после правок «пустым» (не считая include-guard'а и include-директив, вырезает их и проверяет остаток на пробельность), и распознаёт классический include-guard `` `ifndef``/`` `define``/`` `endif``. |
| `include.go` | `includeIndex` — индекс путей для резолва целей `` `include`` (по относительному пути, по суффиксу пути, по имени файла), нужен, чтобы понимать, кто кого включает. |
| `prune.go` | Типы `Edit`/`EditReason` и общая механика правок: `PlanCommentedDirectives` планирует удаление закомментированных `define`/`undef`/`ifdef…endif` (спаривание `` `ifdef``…`` `endif`` — только внутри сплошных комментариев, без активного кода между ними; слово-директива в середине прозы не считается); `normalizeEdits`/`expandToWholeLines`/`ApplyEdits` — сортировка, слияние пересекающихся правок, идемпотентное расширение до целых строк и применение к исходнику. |
| `deadbranch.go` | `PlanDeadBranches` — разбирает вложенные `` `ifdef``/`` `ifndef``/`` `elsif``/`` `else``/`` `endif`` в дерево блоков (`parseCondBlocks`, директивы внутри тел макросов пропускаются) и решает, какая ветка живая: `condTimeline` ведёт пофайловую хронологию `` `define``/`` `undef``/`` `undefineall``, `CondEnv.Elsewhere` — макросы других файлов и внешние (консервативно «определены»). Мёртвые ветки вырезаются, `` `elsif`` промоутится в `` `ifdef``. |
| `scrub.go` | Финальный проход после каскада очистки: `scrubRemovedMacros`/`removedDefineNames` находят имена макросов, чьи `define` полностью удалены и нигде больше не определены, `planMacroScrub` вычищает их упоминания из оставшихся файлов — в комментариях как подстроку, в коде только целыми токенами, строковые литералы не трогает. |
| `cleaner.go` | `Cleaner.Clean` — точка входа очистки: сканирует вход (в режиме `.files` сначала раскрывает `` `include``-замыкание через `includeClosure`), для каждого файла заводит `fileState`, гоняет `cascade` (раунды: вырезать мёртвые ветки → удалить ставшие ненужными файлы, пока что-то меняется), затем `scrubRemovedMacros`, и материализует результат — либо копию всего дерева (`materialize`), либо только перечисленных `.files`-файлов с их заголовками (`materializeFiles`), либо ничего при `-dry-run`. |

## Поток данных

1. `Scanner` (`scanner.go`) читает файлы через `FileSystem` и прогоняет каждый через `ScanSource` (`lexer.go`) → `FileReport`.
2. Обычный режим отчёта: `FileReport`'ы агрегируются в `Summary` (`summary.go`).
3. Режим очистки: `Cleaner` (`cleaner.go`) оборачивает каждый `FileReport` в `fileState`, планирует правки через `prune.go` и `deadbranch.go`, использует `include.go` для резолва `` `include`` и `emptiness.go` для решения об удалении файла, повторяя раунды, пока правки не перестанут появляться; в конце `scrub.go` подчищает следы удалённых макросов и `cleaner.go` пишет результат на диск через `FileSink`.
